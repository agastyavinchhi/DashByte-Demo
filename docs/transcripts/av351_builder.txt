`clean_row` ([pipeline/preprocess.py:108](pipeline/preprocess.py:108)) decides what happens to **one raw order**: keep it (and turn it into a features row) or reject it (and say why).

## What goes in, what comes out

```python
clean_row(row, seen_ids) -> (features, None)   # kept
                         -> (None, reason)     # rejected
```

- **`row`** is one line from a raw CSV, e.g. `{"order_id": "ORD-3f9a…", "timestamp": "2026-09-28T14:02:01Z", "distance_km": "6.4", …}`. All values are strings, because that's what CSV gives you.
- **`seen_ids`** is a set of order IDs already seen *in this file*. The caller creates one empty set per file and passes the same set for every row, so `clean_row` can spot duplicates.
- It always returns a pair, and exactly one side is filled in. The caller never has to guess: if `features` is `None`, there's a reason.

## The steps, in order

The first rule a row fails decides its reason, and later rules aren't checked.

**0. Tidy up.** Surrounding spaces are stripped from every field. A field that's missing entirely (a short line) becomes `""`, so it's caught as blank instead of crashing.

**1. `duplicate_id`:** if this ID is already in `seen_ids`, reject. Otherwise add it to `seen_ids`.
- The ID is claimed *before* the other checks. So if the first `ORD-X` is rejected for a `999.0` distance, a later `ORD-X` is still a duplicate. This is the case in the golden batch, and it matches how the simulator counts duplicates.
- A blank ID is skipped here and falls through to the next rule, so it's reported as `blank`, not as a duplicate of another blank.

**2. `blank`:** any field is empty after stripping.

**3. `bad_timestamp`:** the timestamp must look exactly like `YYYY-MM-DDTHH:MM:SSZ` *and* be a real date. Two checks are needed: the pattern rejects `"2026-9-28…"`, and the real parse rejects month 13.

**4. `not_a_number`:**
- distance and value must be real numbers; `"nan"` and `"inf"` don't count;
- prep must be a whole number: `"18"` or `"18.0"` passes, `"12.5"` and `"n/a"` fail.

**5. `out_of_range`:** each number must satisfy `low < value ≤ high`, using `VALID_RANGES`:

| Field | Allowed |
|---|---|
| distance_km | more than 0, up to 50 |
| prep_minutes | more than 0, up to 120 |
| order_value | more than 0, up to 1000 |

This is what catches the simulator's `-1.0` and `999.0` distances. The bounds are deliberately about what a real order could look like, not a copy of the simulator's ranges.

**6. `bad_label`:** `was_late` must be exactly `"0"` or `"1"`. `"yes"` is rejected, not guessed.

**7. Build the features row.** A row that passes everything becomes:

```
order_id, timestamp, hour, is_peak, distance_km, prep_minutes, order_value, was_late
```
- **`hour`** is the `HH` of the UTC timestamp, so `…T18:05:00Z` gives `18`.
- **`is_peak`** is `1` if `hour` is in `PEAK_HOURS` (11–13 or 17–20), otherwise `0`.
- **Numbers are rewritten in one fixed format:** distance with 1 decimal, prep as an integer, value with 2 decimals. `" 6.40 "` becomes `6.4` and `"18.0"` becomes `18`, so training always sees one consistent shape.
- **`was_late`** is kept as-is, as the last column.

## Why the order of checks matters

Checking cheap, broad problems first gives each rejected row the most useful single reason:
- A row with a blank value *and* a negative distance is reported as `blank`, because there's no point range-checking a row that's missing data.
- A row with `n/a` prep *and* a `yes` label is reported as `not_a_number`.

The tests pin this order, and `REJECT_REASONS` lists the reasons in the same order.

## What it deliberately doesn't do

- **No file I/O and no logging.** It only judges one row. Reading files, writing the features and rejects files, and counting reasons all happen in `process_file`, which calls `clean_row` once per row. That's why the plan's boundary tables can be tested row by row with no files involved.
- **No fixing.** It never guesses that `"yes"` means `1` or fills in a blank value. A bad row is rejected and kept in `data/quality/` with its reason, so nothing disappears silently.

## How `train_model` works

[pipeline/train.py](pipeline/train.py) takes every feature row in time order, each as `(distance_km, prep_minutes, was_late, timestamp)` strings, and returns a fitted model plus a metrics dict. Step by step:

1. **Guard: enough data.** With fewer than 50 rows it raises `NotReady("need at least 50 rows")`. That isn't an error; the loop logs `waiting: …` and tries again later.
2. **Build the arrays.** `X` is one row of `[distance_km, prep_minutes]` per order, as floats, and `y` is `was_late` as 0/1. The timestamp isn't used for learning.
3. **Split by time, with no shuffling.** The newest 20% of rows become the test set and the oldest 80% the training set. This asks the honest question: "does a model trained on the past predict the next orders?" It also makes the split deterministic.
4. **Guard: both outcomes present.** If the training part is all on-time or all late, there's nothing to learn, so it raises `NotReady("need both on-time and late orders")`.
5. **Fit.** It fits `LogisticRegression()` with default settings on the two raw columns, with no scaling, so the coefficients read directly as "change in log-odds of being late per km / per prep minute".
   - This happens inside `np.errstate(...)` to silence the bogus NumPy/macOS warnings.
   - Straight afterwards it checks that the coefficients and probabilities are finite, so a real numerical failure still raises.
6. **Score on the held-out 20%:**
   - accuracy, precision, recall and F1;
   - ROC AUC, left as `null` if the test set has only one class, since it's undefined then;
   - `baseline_accuracy`, the score of always guessing the most common outcome, so the room can see the model beats a naive guess;
   - `late_rate_test`;
   - the coefficients and intercept.

   Everything is rounded to 3 decimals, and `data_through` is the newest timestamp.

It doesn't read files, write files or log anything; `run()` and `publish()` do that. So the same rows always give the same model and the same numbers, which is what the determinism test checks.

## When does the logistic regression stop?

Fitting is an optimisation. The default solver, **L-BFGS**, repeatedly adjusts the two coefficients and the intercept to lower the **log loss** (how wrong the predicted probabilities are) plus a small L2 penalty that keeps the coefficients from growing huge (`C=1.0`). In scikit-learn 1.6.1 it stops at whichever of these happens first:

| Stop condition | Setting | Meaning |
|---|---|---|
| **Gradient is tiny** | `gtol = tol = 1e-4` | The loss surface is essentially flat in every direction (largest gradient component ≤ 0.0001): it's at the minimum. This is the normal, converged stop. |
| **Progress stalls** | `ftol ≈ 1.4e-14` (64 × machine precision) | The loss improved by a negligible relative amount between steps, so further steps can't meaningfully help. Also counts as converged. |
| **Out of iterations** | `max_iter = 100` | It gives up after 100 steps and emits a `ConvergenceWarning` ("lbfgs failed to converge"). The model is still usable but may not be fully optimal. |

A step can also fail if the line search (finding how far to move) can't find a better point within `maxls = 50` tries. That also produces a warning.

**What actually happens on our data:** I measured it on simulator output run through preprocess:

| Rows | Iterations used (max 100) | Warnings |
|---|---|---|
| 417 (≈ `v0001`) | 18 | none |
| 837 (≈ `v0002`) | 20 | none |
| 5,000 | 19 | none |

So it stops on the **tiny-gradient** condition after about 20 iterations, far below the cap, even without feature scaling. The count barely grows with more data, because each iteration looks at all rows at once; more rows make each step slower, not the number of steps larger.

If it ever did hit the 100-iteration cap, you'd see it: the `np.errstate` wrapper only silences NumPy's floating-point flags, not scikit-learn's `ConvergenceWarning`, so that warning would still appear in Terminal 3 and `logs/train.log`.

| 334 (a typical `v0001`) | 1.476 → 1.538 | 0.517 → 0.536 | **4.0% / 3.7%** |
| 4,000 | 1.315 → 1.318 | 0.443 → 0.444 | **0.2% / 0.2%** |

**Why it's unequal:** the penalty charges `w²` in each coefficient's own units, and the pull it exerts is proportional to the coefficient's size. The km coefficient is about 3× larger, because one km matters about as much as three prep minutes, so it's pulled back a little harder. It would be exactly fair only if both features were on the same scale, for example standardised to "per standard deviation".

**Why it's small here:** scikit-learn adds the data's loss over *all* rows, but the penalty is a fixed amount that doesn't grow with the row count. With hundreds of rows the data dominates, and by `v0001` (about 330 training rows) the shrinkage is already around 4%, falling below 1% within a few versions.

**What it does to the story you tell the room:** very little. The simulator's rule is "3 minutes per km", so the km-to-minute coefficient ratio should come out near 3:

| Training rows | Ratio with default penalty | Ratio unpenalized |
|---|---|---|
| 334 | 2.85 | 2.87 |
| 4,000 | 2.97 | 2.97 |

The penalty shaves both coefficients by nearly the same fraction, so their *ratio* barely moves, and the model visibly rediscovers the simulator's 3-minutes-per-km rule. That makes a nice teaching point.

**If you want to remove it,** there are two one-line options, both of which change behaviour the plan specified ("defaults, no scaler"):
- **`LogisticRegression(penalty=None)`:** the coefficients become the exact per-km and per-minute values, with no shrinkage. The risk is that if a batch were perfectly separable the coefficients could grow very large, but the simulator's noise makes that very unlikely.
- **Standardise the features first:** the penalty is then fair, but the coefficients become "per standard deviation", which loses the readable per-km and per-minute meaning the plan chose.

I'd leave the defaults. The bias is at most a few percent at the sizes we publish, it shrinks with every version, and it doesn't distort the km-versus-minute comparison. If you'd rather have exact coefficients, `penalty=None` is the cleaner change, but it's an Architect decision, so I haven't changed any code.
