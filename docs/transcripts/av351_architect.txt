[AGENT]
`is_peak` is a 0/1 column that marks whether an order was placed during a **meal rush**. As planned in Stage 3:

- **Rule:** `is_peak = 1` if the order's `hour` is in **11, 12, 13** (lunch, 11:00–13:59) or **17, 18, 19, 20** (dinner, 17:00–20:59). Otherwise it's `0`.
- **Where `hour` comes from:** the hour of the order's `timestamp` in **UTC**. For example, `2026-09-29T18:42:10Z` gives `hour = 18` and `is_peak = 1`, while `2026-09-29T15:05:00Z` gives `hour = 15` and `is_peak = 0`.
- **Where the hours are defined:** once in the code, as `PEAK_HOURS = {11, 12, 13, 17, 18, 19, 20}` in `pipeline/preprocess.py`.

**Why it's a feature:** in real food delivery, rush hours mean busy kitchens and more traffic, so orders are more likely to be late. `is_peak` gives the model a simple yes/no version of that idea. It's easier to learn from than the raw hour, because hours 12 and 18 are both "busy" even though the numbers aren't close.

**Two limits in our demo:**
1. **It doesn't affect lateness yet.** The simulator decides `was_late` from prep time and distance only, so `is_peak` has no real connection to whether an order is late. The model can't learn anything from it until the simulator gives busy hours a lateness penalty.
2. **It's the same for every row in a live run.** The simulator stamps orders with the current time, so during a class every row has the same `hour`, and the whole `is_peak` column is all 0s or all 1s.
3. **The hours are UTC, not local time.** A 12pm lunch rush in California is 19:00 UTC, so "peak" in the data doesn't line up with the room's clock.

If you want `is_peak` to matter in the demo, I can plan a small simulator change: spread timestamps across the day and add a few minutes of delay to orders placed during peak hours. Then the model would have a real rush-hour effect to find.

Yes, a few. The first one fixes a real gap in the plan; the rest are improvements.

**1. A half-published version could block training for good (recommend fixing).**
If train crashes after writing `model_v0003.joblib` but before its `.json`, `v0003` is left half-published. The plan says the next version is "highest existing + 1", but it doesn't say whether a `.joblib` with no `.json` counts. If only `.json` files count, train will try `v0003` again, refuse to overwrite it, and fail on every poll.
- **Fix:** work out the next version number from both `.joblib` and `.json` files, so the next publish goes to `v0004`. Leave the orphaned file alone, log it once, and add a unit test for this case.

**2. Record the library versions in the metrics file.**
A `.joblib` file is a Python pickle. It can break, or quietly behave differently, if inference runs with a different scikit-learn version.
- **Fix:** add `sklearn_version` and `python_version` to the `.json` file. Inference can then refuse a mismatched model with a clear message instead of an odd error. That's two extra keys and a regression-test update.

Train always publishes, and inference will pick the newest version. So a worse model would go live automatically. For a demo that's fine, but it should be a deliberate choice. Two cheap options:
- Add `beats_baseline: true/false` to the `.json` file so the Model Pulse dashboard can flag a bad version.

Explain what make logs does and why it staking so long when i run it

[AGENT]
`make logs` isn't slow or stuck. It's meant to run until you stop it.

**What it does:**
1. It finds the logs folder (normally `logs/`).
2. If there are no logs yet, it prints `no logs yet: start the stack with make run` and exits.
3. Otherwise it runs `tail -n 5 -F logs/*.log`. That prints the last 5 lines of each log, labelled `==> logs/simulator.log <==` and so on, then **keeps watching** and prints each new line as it's written.

**Why it seems to hang:** `tail -F` means "follow". It never exits by itself; it waits for more lines. So once the first burst of output appears, the terminal just sits there. That's the expected behaviour.

- Each line appears as soon as a process writes it, but the processes write at different speeds:
  - The simulator writes every 3 seconds.
  - Preprocess, train and infer only check for new files every 15 seconds.
  - Train only logs when it's waiting or publishing.
  - Infer stays quiet after its first `waiting for a checkpoint` line until a model appears, about a minute in.
  - The dashboard only logs while a browser has the page open.
- So pauses of 10–15 seconds between bursts are normal, especially in the first minute.
- **If nothing ever appears,** the stack probably isn't running. Run `make status`. If it shows `0/5 running`, run `make run` first.

**How to use it:**
- Press **Ctrl+C** to stop following. That only stops `tail`; the five background processes keep running. Stop them with `make stop`.
- To see one stage's log once and get your prompt back, run `tail -20 logs/train.log`.
- For faster updates while testing, restart the stack with a shorter poll interval:
  ```bash
  make stop
  ```
  ```bash
  POLL_INTERVAL_SECONDS=3 make run
  ```

If you'd prefer `make logs` to print the recent lines and exit rather than follow, I can change it, or add a separate snapshot target such as `make logs-once`.
